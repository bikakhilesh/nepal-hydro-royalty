# Working on this repository

**Read `README.md` first, and read it properly.** It is not an overview — it
carries the operating rules, and its *Data traps handled in code — do not "fix"
these by hand* section is thirty specific findings that each cost something to
learn. A change that contradicts one of them is almost always a regression that
looks like a cleanup.

This file is only what the README does not yet cover.

## The one rule to internalise before touching anything

`hydro.py` and `template.html` are the only files edited by hand. Everything
else is generated or synced, and a hand-edit to it is overwritten by the next
scheduled run — silently, with no error and no diff to explain where the change
went. Rebuild instead:

```bash
python hydro.py            # writes nepal_hydro.html + dashboard.json
python hydro.py --stats    # reconciliation summary, writes nothing
```

The build is byte-identical across runs and across machines. That makes
"rebuild, then check `git status` is clean" a real verification rather than a
hope, and it is the cheapest way to prove a change did what you think. Use it.

## The listed-company layer, which the README predates

Three CSVs are **synced from upstream by CI** and are not edited here:

    scalper_hydro_combined.csv   scalper_hydro_comparative.csv   nepse_dividends.csv

Two are **hand-maintained and are the authority** — correct them in place:

    scalper_company_lookup.csv   scalper_plf_input.csv

`scalper_company_map.csv` is generated by `python hydro.py companies`.

### The calendar trap

The royalty register's fiscal year runs **Asar to Jestha**. The Nepali
accounting year the companies file on runs **Shrawan to Asar** — one month
later. Any join between register data and company filings must re-cut monthly
rows onto the accounting year first. Skipping it raises nothing; it just returns
numbers that are quietly wrong. Re-cutting moved median company-year error from
3.6% to 0.55% and exact agreement from 102 of 310 to 194. Bikram Sambat is
AD + 57, so AD 2024/25 is BS 2081/82, the register's `081/82`.

Because agreement is the normal case, a company that disagrees badly with its
own filings is usually a mapping error rather than a data problem. Two were
found exactly that way.

### Rules on this layer

- **Never infer a plant load factor.** Blank in `scalper_plf_input.csv` means
  the figure was not available. A plausible guess is worse than the gap, because
  the gap is honest. Do not re-research a plant already resolved.
- **Say what cohort a figure was struck on.** A median that silently mixes bases
  is a defect here, not a rounding matter. The market tab runs on the screened
  cohort — book value above the NPR 100 par, trailing EPS above zero — and says
  so on the page; the other tabs keep their own basis and say so too.
- **EPS is trailing twelve months.** The per-quarter annualised figure is not
  carried anywhere.
- **Bonus and cash dividends are never summed.** Most cash paid beside a bonus
  issue is the 5% withholding tax grossed up, not a distribution.

## Automation: three workflows, not the two the README lists

`scalper-sync.yml` (Sync external series) runs first and feeds
`refresh-data.yml` (Refresh from RMS), which feeds `pages.yml` (Deploy
dashboard) — chained on `workflow_run`, not on guessed cron offsets, so one
push drives the sequence in order.

The sync workflow refuses a file that has shrunk. Keep that. A change letting a
truncated upstream file through would replace good data with less of it, on a
schedule, unattended — and `.github/scripts/guard.py` downstream checks for
*disappearance* of plants and plant-years, which a row-count floor cannot do.
